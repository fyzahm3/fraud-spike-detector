Methodology, stated as constraints

The threshold never sees the test split

No function in the training code accepts the test frame. Hyperparameters and the decision threshold are chosen on validation and frozen. {{ h.help('threshold', '-method') }}

Streaming features look only backwards

Every graph and spike feature for a given row is computed from strictly earlier rows, on half-open windows with deterministic tie-breaking. Verified against brute-force references and future-corruption tests. {{ h.help('leakage', '-method') }}

Same seed, same model

Training is pinned to a fixed seed and thread count, so a rerun produces byte-identical models and scores. A test asserts it.

The model does not write numbers

Scores, confidence, costs, and recommendations are computed before the language model is called; it contributes the prose only. {{ h.help('llm_prose') }}

Dataset study — and the gap this does not close {{ h.help('dataset_gap') }}

The primary dataset is IEEE-CIS Fraud Detection: real US e-commerce card-not-present transactions. India's payment ecosystem is driven heavily by UPI, IMPS/NEFT, and wallets, which differ from US card rails in three ways that matter to this architecture.

Where the transfer is not automatic
Dimension Card-not-present, as modelled here UPI, as it actually behaves
Entity topology Card fields, billing address, email domain Virtual payment addresses, device identifiers, bank handles, account numbers
Velocity Settlement over 1–3 days; hourly and daily windows fit Instant, around the clock; multi-hop fan-out unfolds in seconds
Typology Stolen card details used remotely SIM-swap and OTP compromise, collect-request abuse, QR social engineering

Adapting this to UPI would mean replacing card-node features with directed address-to-address transfer edges, shortening the rolling windows from hours to seconds, and adding device and geolocation telemetry. That work is described rather than claimed: no synthetic UPI data was generated, because fabricated data yields fabricated metrics.
