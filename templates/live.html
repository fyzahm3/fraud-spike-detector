Live ingestion

This payment was never in the training data. It is scored anyway — by the model that only knows what a payment rail can tell it.

Everything else on this site is measured on a held-out slice of a dataset. This page is not. A real payment is created against a real payment gateway, a real webhook comes back signed, and the item below is that payment — scored at the instant of authorization, by a model trained for exactly that moment.

Test mode only. One ₹1 order against the sandbox. A key that is not a test-mode key is refused before any network call is made, so this control cannot reach a live payment environment.

The distinction that matters

A fraud model is only as good as the history behind the transaction. The full model reaches AUC-PR {{ '%.4f'|format(full_auc) }} because it can see that a card has appeared on four devices this week, that an email domain clusters with three charged-back accounts, that an address has been reused at 3 a.m. twice.

None of that exists at the moment a payment is authorized. The webhook carries an amount, a card network, a card type, an email domain and a timestamp. {{ gw_features }} usable fields against {{ full_features }}.

So this payment is scored by a gateway model — same dataset, same chronological split, same protocol, restricted to those {{ gw_features }} fields. It reaches AUC-PR {{ '%.4f'|format(gw_auc) }}. That gap is not a flaw in the demo; it is the measurement. It is what an entity’s accumulated history is worth, stated as a number.

How this becomes a production system

Two passes, because the data arrives at two different times.

What runs here is the first pass. The architecture below is what a real integration looks like, and the only thing separating this demo from it is a durable store of entity history — not a different model, and not a different idea.

Pass 1 — at authorization

running now

Latency budget: milliseconds. The payment is waiting.

A client — Razorpay or any other gateway — posts a signed webhook. The signature is verified over the raw bytes before anything is parsed. The payload is projected onto the seven fields the gateway model was trained on: amount, hour, weekday, card.network, card.type, email domain, issuing country.

A field the webhook did not send stays missing. It is never defaulted to a plausible value to improve the score — XGBoost handles missingness natively, and a filled-in value would be describing the fill, not the payment.

Output: a real probability, and a threshold decision. Good enough to triage; explicitly labelled as such.

Pass 2 — once history exists

not built here

Latency budget: seconds to minutes. Nobody is waiting.

The payment is written to an entity store keyed by card, email, device and address. From that store the causal graph features are computed the same way src/features/graph_features.py computes them on the dataset today: rolling 24h and 7d co-occurrence counts, plus a 48h exponentially-decayed measure of fraud among an entity’s neighbours — each built from strictly earlier transactions only, which is the property the whole evaluation rests on.

With that history in hand the payment is re-scored by the full model, grouped into spike events per entity, and written to the review queue with a brief.

Output: the {{ '%.4f'|format(full_auc) }}-grade judgement — minutes late, and worth the wait.

What is actually missing, precisely

1. A durable entity store. The graph features need an entity’s prior transactions. One payment has no neighbours. This demo runs on a free tier whose filesystem is wiped on every deploy, so history cannot accumulate here — a production deployment would keep it, and the same feature code would then run unchanged.

2. Identity signals at authorization time. IEEE-CIS carries a device and browser fingerprint block. A gateway webhook does not. A real integration would take these from the checkout session rather than the payment object.

3. The masked V1–V339 block cannot be reconstructed at all. Those are proprietary engineered features with no published definition — roughly 340 of the full model’s {{ full_features }} columns. A production system would not port them; it would engineer its own equivalents from its own data and retrain. This is the honest reason the full model, as trained, cannot be pointed at a live rail — not the reason a live rail cannot be scored.

What happens, in order

01 — ORDER

One order is created

A single call to the orders endpoint, for a fixed one-rupee amount that is not caller-supplied. This is the only outbound payment-rail call the application can make: there is no path to a refund, a capture, a payout, or a subscription, and a test scans for one on every run.

Out: order id

02 — VERIFY

Signature checked before anything is read

The webhook body is HMAC-SHA256 verified against the signing secret, over the raw bytes exactly as received. A payload that fails is rejected with a 400 and is never parsed, stored, or logged. A repeated event id is recognised as a retry and ignored rather than queued twice.

In: signed webhook  ·  Out: verified payload

03 — QUEUE

Queued as explicitly unscored

The item enters the same review queue as everything else, marked with its own type, served with a null score and an explicit unscored flag, and rendered on its own branch — different wording, different labels, dashed border. Not a colour difference: a viewer must not be able to mistake it for a scored item.

Out: unscored review item

Why there is no number here

The feature space does not overlap.

The model was trained on the IEEE-CIS feature space — roughly 430 engineered columns, including a large block of masked proprietary features and the causal graph features derived from an entity’s own transaction history. A payment webhook carries an amount, a currency, a method, an order id, and a timestamp. The two do not overlap.

Filling the roughly 430 absent features with zeros and calling the model would return a number. That number would be a property of the padding, not of the payment. This project already shipped one metric that was an artifact of its data rather than its model, found it, and deleted both the metric and the script behind it. Manufacturing a second one so a demo looks more complete is not a trade it makes.

Real-time scoring would need the feature space derived from live data: a durable per-entity history for the rolling co-occurrence features, identity signals available at authorisation time, and a replacement for the masked proprietary block, which has no public definition and cannot be reconstructed at all.
