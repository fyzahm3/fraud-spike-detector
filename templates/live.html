Live ingestion {{ h.help('live_unscored') }}

A real payment, on a real payment rail, arriving in the review queue over a signature-verified webhook — and carrying no risk score, on purpose.

Test mode only. Creates one ₹1 order against Razorpay's sandbox and opens their hosted checkout. A key that is not a test-mode key is refused before any network call is made, so this control cannot reach a live payment environment. Recording the order requires the demo password; reading this page does not.

What happens, in order

  1. 1

    One order is created

    A single call to the orders endpoint, for a fixed one-rupee amount that is not caller-supplied. This is the only outbound payment-rail call the application can make: there is no code path to a refund, a capture, a payout, or a subscription, and a test scans the package for one on every run.

  2. 2

    The signature is verified before anything is read

    The webhook body is HMAC-SHA256 verified against the signing secret, over the raw bytes exactly as received. A payload that fails is rejected with a 400 and is never parsed, stored, or logged. A repeated event id is recognised as a retry and ignored rather than queued twice.

  3. 3

    It is queued as explicitly unscored

    The item enters the same review queue as everything else, marked with its own type, served with a null score and an explicit unscored flag, and rendered on its own branch in the interface — different wording, different labels, dashed border. Not a colour difference: a viewer must not be able to mistake it for a scored item.

Why there is no number here

The model was trained on the IEEE-CIS feature space — roughly 430 engineered columns, including a large block of masked proprietary features and the causal graph features derived from an entity's own transaction history. A payment webhook carries an amount, a currency, a method, an order id, and a timestamp. The two do not overlap.

Filling the roughly 430 absent features with zeros and calling the model would return a number. That number would be a property of the padding, not of the payment. This project already shipped one metric that was an artifact of its data rather than its model, found it, and deleted both the metric and the script behind it. Manufacturing a second one so a demo looks more complete is not a trade it makes.

Real-time scoring would need the feature space derived from live data: a durable per-entity history for the rolling co-occurrence features, identity signals available at authorisation time, and a replacement for the masked proprietary block, which has no public definition and cannot be reconstructed at all. A production system would train on its own feature space rather than port this one. Until then, ingestion and scoring are separate capabilities here, and the queue says so on every affected row.
