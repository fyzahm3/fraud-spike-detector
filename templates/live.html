This item is not from a dataset. A real order is created against a real payment gateway in test mode, and the signed webhook that comes back is verified before anything is parsed.

Why this score is different {{ h.help('gateway_model') }}

The full model reaches AUC-PR {{ '%.4f'|format(full_auc) }} because it can see an entity's accumulated history — a card on four devices this week, an email clustering with charged-back accounts. None of that exists at the instant a payment is authorized.

So this payment is scored by a gateway model restricted to the {{ gw_features }} fields a webhook actually carries. It reaches AUC-PR {{ '%.4f'|format(gw_auc) }}. That gap is the measurement: what an entity's history is worth, stated as a number.

Two passes, because the data arrives at two different times

What runs here is the first pass. The second is the same architecture and the same feature code, running against a store of entity history instead of a dataset.

Pass 1 — at authorization

running now

Latency budget: milliseconds. The payment is waiting.

A client posts a signed webhook. The signature is verified over the raw bytes before anything is parsed. The payload is projected onto the seven fields the gateway model was trained on: amount, hour, weekday, card.network, card.type, email domain, issuing country.

A field the webhook did not send stays missing — never defaulted to a plausible value. XGBoost handles missingness natively; a filled-in value would describe the fill, not the payment.

Pass 2 — in production

how it deploys

Latency budget: seconds to minutes. Nobody is waiting.

The payment is written to an entity store keyed by card, email, device and address. From that store the causal graph features {{ h.help('graph_features', '-live') }} are computed by the same graph_features.py that runs on the dataset today, each built from strictly earlier transactions only.

With that history in hand the payment is re-scored by the full model, grouped into spike events, and written to the review queue with a brief — the {{ '%.4f'|format(full_auc) }}-grade judgement, minutes late.

What connecting a client actually involves

The architecture is complete and proven on {% if split %}{{ '{:,}'.format(split.splits.train.n_rows + split.splits.validation.n_rows + split.splits.test.n_rows) }}{% endif %} real transactions. Going live is integration work, not new research: an entity store so the graph features have a past to compare against (this demo runs on a free tier whose disk is wiped on every deploy, which is the only reason it is not accumulating here), and the feature block refitted to the client's own data — roughly 340 of the full model's {{ full_features }} columns are the dataset provider's own engineered signals.

What happens, in order

ORDER

One order is created

A single call to the orders endpoint, for a fixed one-rupee amount that is not caller-supplied. There is no path to a refund, a capture, a payout, or a subscription, and a test scans for one on every run.

Out: order id

VERIFY

Signature checked before anything is read

The webhook body is HMAC-SHA256 verified against the signing secret, over the raw bytes exactly as received. A payload that fails is rejected with a 400 and never parsed, stored, or logged. A repeated event id is recognised as a retry and ignored.

In: signed webhook  ·  Out: verified payload

QUEUE

Queued as explicitly unscored

The item enters the same review queue as everything else, marked with its own type, served with a null score and an explicit unscored flag, and rendered on its own branch — a viewer must not be able to mistake it for a scored item.

Out: unscored review item
