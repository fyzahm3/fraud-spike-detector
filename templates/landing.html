The problem

A payment company loses money twice, and usually measures once.

The first loss is the fraudulent transaction that settles. The second is the real customer whose payment is refused at checkout, who calls support, and who may not come back. Both are denominated in money.

Most detection systems report recall, precision, and an ROC curve. None of those say what the false positives cost. A model can improve on every published metric while making the business worse, and nothing in the report will show it.

How it works

Three stages. Only the last one writes prose.

01 — SCORER

XGBoost risk score

Each transaction is scored 0–1 for fraud risk. Trained on the {% if split %}{{ '{:,}'.format(split.splits.train.n_rows) }}-row{% endif %} chronological training split of the IEEE-CIS public dataset — real, anonymized card transactions.

In: transaction row  ·  Out: score 0–1

02 — PATTERN WATCHER

Bursts, not outliers

One odd transaction is noise; a burst is signal. Rolling 1h and 24h windows per entity, normalized against that entity’s own baseline, so a busy card is not flagged for being busy. A graph links entities that share a device, email domain, or address. {{ h.help('graph_features') }}

In: score + entity history  ·  Out: ranked spike

03 — EXPLAINER

A brief a human can act on

A language model writes a plain-English brief for each flagged item. It writes only the prose. Confidence, cost estimate, and recommended action are computed in Python before the model is ever called. {{ h.help('llm_prose') }}

In: spike + computed fields  ·  Out: review brief

The system cannot act

It has no code path that can act on a payment in either direction. A human reviewer makes every decision, and the absence of that path is enforced by tests, not policy. {{ h.help('human_decides') }}

What this is

Trained on real payment data. Running right now.

Not a mock-up and not a simulation. A model was trained on {% if split %}{{ '{:,}'.format(split.splits.train.n_rows + split.splits.validation.n_rows + split.splits.test.n_rows) }}{% endif %} real card transactions, measured on data it had never seen, and it is serving predictions on this page as you read it.

  • Real transactions

    {% if split %}{{ '{:,}'.format(split.splits.train.n_rows + split.splits.validation.n_rows + split.splits.test.n_rows) }}{% endif %} anonymised card payments from the IEEE-CIS public dataset — real money, real fraud, real outcomes.

  • It learns behaviour, not rules

    Beyond the payment itself, the model reads how a card, email, device or address has behaved over the previous hours and days. Each of those signals is built only from what came before it, so nothing the model sees at scoring time is something it could not have known.

  • It scores a payment as it arrives

    A real payment from a payment gateway is scored the moment it arrives, by a model trained for that exact moment — the gateway model. Anything with history behind it goes to the full model instead. Every score says which model produced it.

  • A person makes every call

    The system scores, groups and explains. It has no way to act on a payment in either direction. A reviewer decides, and every decision is written permanently.
