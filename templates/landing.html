How it works

  1. 1 · Score

    Every transaction, on its own merits

    A gradient-boosted model scores each transaction. Alongside the tabular features it reads twelve causal co-occurrence features describing how a card, email, device, or address has behaved over the previous hours and days — each computed from strictly earlier transactions only. {{ h.help('graph_features', '-step') }}

  2. 2 · Aggregate

    Bursts, not just outliers

    Scores roll up per entity over 1-hour and 24-hour windows and are compared against that entity's own earlier baseline. Coordinated abuse shows up as a burst that a per-transaction score alone reads as unrelated events. {{ h.help('spike') }}

  3. 3 · Explain

    A brief a reviewer can argue with

    The score, the confidence band, the estimated cost of a false positive, and the recommendation are all computed in Python. A language model writes the summary paragraph and nothing else, so it cannot introduce a number or change a recommendation. {{ h.help('llm_prose') }}

  4. 4 · Decide

    The reviewer holds the decision

    Items land in a queue with an append-only audit log. Resolving one updates a status and writes a permanent row; a correction is a new row, never an edit. The action is required and validated — a decision is never recorded by default.

What this deliberately does not claim

It does not act on payments

There is no interface to any payment action anywhere in the codebase, in either direction. This is verified by source scans in the test suite rather than asserted in a policy document.

Live payments are not scored

The live-ingestion demo receives a real test-mode payment and queues it marked explicitly as unscored, because a payment webhook does not contain the feature space the model was trained on. {{ h.help('live_unscored') }}

The training data is US card data

It is not UPI data, and no synthetic UPI data was generated to stand in for it. The gap is documented rather than filled. {{ h.help('dataset_gap') }}

No cross-dataset claim

Validation on a second payment rail was scoped and not completed in the build window, so no transferability claim is made. An earlier revision reported perfect scores on a placeholder generator; those were an artifact of label leakage, and both the numbers and the script producing them were deleted.
